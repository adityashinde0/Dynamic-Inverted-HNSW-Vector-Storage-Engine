PS-005 is a storage engine built for workloads that never stop writing. A durable write-ahead log and in-memory table absorb new vectors continuously, while immutable, quantized segments on disk stay searchable — so ingestion and similarity search run at the same time, on separate structures, without blocking each other.

SHEET 02 The write path WAL → MemTabledurability before ack

Every write lands durably before it's acknowledged.

Each incoming vector is appended to the write-ahead log first — an ordered, crash-safe record of everything the engine has accepted — and only then applied to the in-memory MemTable, where it becomes immediately visible to queries.

The WAL is the only structure a write must touch before the client hears back. Everything downstream of it can fail and be rebuilt.

  1. Append to the WAL

    The vector and its metadata are appended sequentially to the write-ahead log on disk. Sequential appends mean this step is cheap even under sustained high-throughput ingestion.

  2. Insert into the MemTable

    The same write is applied to an in-memory, sorted structure. Reads issued a moment later will see it — the MemTable is always the freshest source of truth.

  3. Flush when full

    Once the MemTable reaches its size threshold, it's flushed to disk as a new immutable segment, and a fresh MemTable takes over writes. Flushing never blocks incoming vectors.

SHEET 03 The read path Segments → HNSWquantized, per-segment index

Each segment carries its own index.

When a segment is written, its vectors are quantized to shrink their footprint, and an HNSW graph is built over them — a layered proximity structure that lets a query jump toward its nearest neighbors in a handful of hops instead of scanning every vector.

A query never touches raw vectors directly: it walks the graph, narrowing in on the closest candidates one hop at a time, the same way the visualization to the right walks toward a query point.

fig. 2 — HNSW proximity graph simulated
quantization

Smaller footprint

Vectors are compressed before they're indexed, trading a small amount of precision for a much smaller memory and disk footprint per segment.

per-segment index

Independent, immutable

Each segment's HNSW graph is built once and never modified — only replaced wholesale when segments are merged.

query router

Concurrent fan-out

A Go gRPC router dispatches each query to the MemTable and every active segment at once, gathering candidates in parallel.

final merge

One ranked top-k

Candidates from every source are merged and re-ranked into a single ordered result before anything is returned to the caller.

SHEET 04 Compaction segment mergeLSM-style leveling

Small segments merge so search stays fast.

Left alone, flushing would leave behind an ever-growing pile of small segments, and every query would need to check more of them. A background compaction process merges related segments together, combining their vectors, discarding anything since deleted, and rebuilding one HNSW graph over the result.

Compaction runs alongside ingestion and querying — it reads and writes segments, but never locks the ones still serving traffic.
